## 0. 一分钟了解这个项目

**一句话**：ZigoAI Mini 是一个 AI 销售助手 —— 它读懂客户消息，判断客户处于销售漏斗的哪一步，建议销售下一步做什么，并给出一句可以直接发出去的话。

**业务闭环**：

```
客户发来消息
  ↓
系统读取历史对话 + 客户当前状态 + 企业销售规则
  ↓
AI 判断：客户意图 / 销售阶段 / 下一步动作 / 是否需人工 / 建议回复
  ↓
系统用「状态机」裁决：哪些采纳、哪些拦下（终态保护、阶段不回退）
  ↓
销售看到建议 → 可修改 → 点击发送
  ↓
消息进入聊天记录，成为下一轮判断的上下文
  ↓
客户状态被更新（阶段 / 意图 / 是否需人工）
```

**线上地址**：http://42.194.164.30:8080

**演示账号**（密码统一 `Zigo@2026`）：

| 企业 | 角色 | 账号 | 能看到什么 |
|---|---|---|---|
| 乐蒙亲子游泳 | 销售 | `sales@lemeng.demo` | 只有自己名下的 3 个客户 |
| 乐蒙亲子游泳 | 主管 | `manager@lemeng.demo` | 乐蒙全部客户 + 可改企业规则 |
| 机械之家 | 销售 | `sales@jixie.demo` | 只有自己名下的 3 个客户 |
| 机械之家 | 主管 | `manager@jixie.demo` | 机械之家全部客户 + 可改企业规则 |

> 两家企业的销售规则与转人工标准**刻意做得不同**，同一个客户消息在两家企业下会得到不同的判断 —— 这是核心任务 5 的验收方式。

## 1. 系统全景

### 1.1 架构

```
浏览器
  │ Cookie（服务端签名的会话）
  ▼
Next.js 全栈（前端页面 + API Route = 后端）
  ├─ requireAuth() ─── 所有请求的第一道门：租户与角色从这里来
  ├─ repositories/ ─── 数据访问层：强制注入 tenant 作用域（隔离的唯一入口）
  ├─ agent/ ────────── 唯一一条 AI 主干 pipeline + 6 个钩子
  └─ DeepSeek API ──── json_object 结构化输出
  ▼
PostgreSQL（7 张表）
```

### 1.2 数据模型（7 张表）

| 表 | 作用 | 关键字段 |
|---|---|---|
| `Tenant` | 企业（租户） | `salesGoal` 销售目标、`rules` 销售规则、`handoff` **交接规则**、`tone` 语气、`forbidden` 禁止事项 |
| `User` | 用户 | `role`（SALES / MANAGER）、`passwordHash` |
| `Customer` | 客户 | `assigneeId` 归属销售 |
| `Message` | 聊天记录 | `role`（CUSTOMER/SALES）、`clientMessageId`（幂等键）、`batchId`（连续消息合并） |
| `CustomerState` | **客户销售状态** | `leadStage`、`intent`、`needHuman`、`lastCustomerMessageAt`（跟进判定依据）、`followUpCount`、`version`（乐观锁） |
| `AiSuggestion` | **AI 判断 + 调用审计** | 六个必需字段 + `rulesApplied`、`stateAdjustments`、`handoffNotes`、`rawRequest/rawResponse`、token、成本、`sentMessageId/finalReply`（采纳留痕） |
| `FollowUpTask` | 跟进任务 | `status`、`attempt`（幂等键）、`reason` |

### 1.3 AI 主干 pipeline（一条，不是一堆）

```
载入上下文（企业规则 + 交接规则 + 客户 + 旧状态 + 历史消息 + 本轮新消息）
  → 组装 Prompt
  → 调用 DeepSeek（response_format=json_object）
  → 宽松解析 + zod 严格校验
  → 不合格：带错误信息重试一次（若是被 max_tokens 截断则加大预算）
  → 仍不合格：降级为「转人工」兜底建议（页面不崩、消息不丢）
  → 状态机裁决阶段（终态保护 / 阶段不回退）
  → 规则守护：确定性校验回复是否踩企业红线（违规回灌重写一次）
  → 交接规则：按企业配置决定本轮是否必须人工介入
  → 事务落库：写 AiSuggestion（含原始请求/响应）+ 乐观锁更新 CustomerState
```

### 1.4 六个进阶钩子（都挂在这条主干上）

| 钩子 | 挂在哪 | 一句话 |
|---|---|---|
| 连续消息合并 | 入口 | 窗口内的多条消息算「一轮沟通」，只调一次 AI |
| 消息幂等 | 入口 | 同一个 `clientMessageId` 只落库一次，不重复调 AI |
| AI 异常处理 | LLM 客户端 | 超时/空内容/坏 JSON/截断 分类处理，重试→降级，绝不让页面崩 |
| 规则守护 | 校验之后 | 企业红线用**代码**兜底，不只靠提示词 |
| Tenant 隔离 | 数据访问层 | 所有查询强制租户作用域，越权一律 404 |
| Follow-up | 定时/手动扫描 | 客户静默超时 → 复用同一条 pipeline 生成跟进建议 |

### 1.5 页面地图

| 路径 | 页面 | 谁可用 |
|---|---|---|
| `/login` | 登录 | 所有人 |
| `/customers` | 客户列表 | 登录后（销售看自己名下，主管看全部） |
| `/customers/new` | 新建客户 | 登录后（主管可指派负责人） |
| `/customers/[id]` | **客户详情（主战场）** | 登录后 |
| `/tenant/config` | 企业规则 + 交接规则 + 规则试跑对比 | 主管可编辑，销售只读 |
| `/ai-logs` | AI 调用审计 / 成本 / 采纳率 | 登录后 |

## 3. 功能详解

### 3.1 登录与角色

- 登录用邮箱 + 密码，密码用 `scrypt` 哈希存储，会话是服务端签名的 httpOnly Cookie
- **`SALES`**：只能看到/操作自己名下的客户
- **`MANAGER`**：能看到本企业全部客户，并且可以修改企业规则
- 跨企业访问**一律 404**（不暴露"这个客户存在但不属于你"）

### 3.2 客户与聊天记录

- 创建客户时会自动建立初始状态（阶段=新客户、意图=待判断）
- 录入"客户消息"时会带一个客户端生成的**幂等键**：网络重试/连点两次不会产生重复消息，也不会重复调用 AI
- 重复提交时界面会提示"检测到重复提交，已按同一条消息处理"

### 3.3 AI 判断卡片怎么看

卡片分两层 —— **销售只需要看主区域，想深究再展开**：

**主区域（销售的视线）**
1. 需不需要人（橙色条：建议人工介入 + 原因）
2. 一行结论：客户意图 · 阶段 · 下一步动作
3. **建议回复**（大字）+ 三个动作：发送 / 改一下再发 / 重新生成

**折叠区「为什么这么判断？」（点开）**
- 判断依据（模型给的理由）
- 引用企业规则（悬停看规则原文）
- 系统对 AI 建议的修正（"AI 建议 X → 采纳 Y"，例如阶段被状态机拦住）
- 销售实际发送内容（如果改过）
- 规则守护提示 / 模型 / 耗时 / token / prompt 版本
- **「查看这次判断的完整链路 →」**：进入链路页，看分段耗时与送进模型的 prompt 原文

| 区块 | 含义 |
|---|---|
| 右上角徽章 | **这次 AI 调用本身是否健康**（调用成功 / 重试后成功 / 已降级为人工 / 调用失败）—— 它不评价判断质量 |
| 元信息行 | 调用时间、模型、耗时、token、prompt 版本 |
| 三格判断 | 客户意图（枚举 + 具体说明）/ 销售阶段 / 下一步动作 |
| 引用企业规则 | AI 自述本次引用了哪几条企业规则（鼠标悬停看规则原文）——**这是"规则真的影响了判断"的证据** |
| 建议人工介入（橙） | AI 建议转人工，并给出原因 |
| 判断依据 | AI 为什么这样判断 |
| 建议回复 | 可直接发送的话 |
| 已发送徽章 | 已按建议发送 / 已修改后发送 |
| 销售实际发送 | 只有被改过才出现 |
| **系统对 AI 建议的修正** | 例如「AI 建议『已流失』→ 采纳『已成交』（终态保护）」——**这一块是"系统不完全信任模型"的可视化** |
| 规则守护提示（红） | 回复踩了企业红线（如未表达兴趣却报了价） |
| 本轮合并 N 条消息 | 连续消息合并生效的证据 |

### 3.4 Customer State 与人工操作

状态卡显示：销售阶段 / 当前意图 / 是否需人工 / 最后客户消息 / 跟进次数 / 状态版本。

**三条硬规则**（AI 无权违反，只有人能改）：

| 规则 | 含义 |
|---|---|
| 终态保护 | 已成交 / 已流失不允许 AI 改动；AI 建议进终态时，系统只把阶段暂存为高意向并强制转人工 |
| 阶段不回退 | 阶段只能保持或前进；回退需人工判断 |
| 需人工只升不降 | AI 只能升级为需人工；解除必须由人工操作 |

**人工操作按钮**：标记人工已处理 / 确认成交 / 确认流失 / 撤销终态（重新激活）。

### 3.5 销售回复与留痕

改完再发 → 系统记录 `sentMessageId / finalReply / sentAt`，于是「AI 建议了什么 → 人改成了什么 → 最后发出去的是什么」三段可追溯，并能算出**采纳率 / 修改率**。

### 3.6 企业规则与交接规则（`/tenant/config`）

**销售规则**：逐条编号注入提示词，可挂"机器校验码"（规则守护用）。

| | 乐蒙亲子游泳 | 机械之家 |
|---|---|---|
| 销售目标 | 推动客户预约线下体验课 | 获取客户行驶证，完成设备与保险方案报价 |
| 规则 R1 | 未表达明确兴趣前不主动报价（**带校验**） | 确认设备与保险需求后优先索取行驶证（**带校验**） |
| 规则 R4 | 不得绝对化承诺（**带校验**） | 不得承诺一定承保/理赔金额（**带校验**） |
| 禁止事项 | 承诺折扣 / 承诺学会游泳 / 承诺健康效果 | 承诺承保 / 承诺最低价 / 承诺理赔金额 |

**交接规则**（什么情况必须交给人工）：

| | 乐蒙 | 机械之家 |
|---|---|---|
| 敏感词 | 退费、投诉到总部、曝光、媒体 | 起诉、律师、监管、曝光、退保、理赔纠纷 |
| 金额阈值 | 5000 元 | **1000 元** |
| 补充说明 | 年卡及以上务必人工确认 | 凡涉及保费、理赔、退保一律人工核保 |

**规则试跑对比**（页面底部）：同一客户 + 同一段历史 + 同一句客户消息，用「当前已保存的规则」与「你正在编辑的草稿」各判断一次，并排看差异，**不落库**。

### 3.7 连续消息合并（窗口是自适应的）

客户连发多条 → 合并为**一轮沟通**，只调用一次 AI。判断完成后卡片标注"本轮把客户连续发送的 N 条消息合并为一次判断"。

**窗口不是一个固定值**，而是对"客户说完了没有"的估计（`src/lib/agent/batch-window.ts`）：

| 客户最后一句 | 窗口 | 为什么 |
|---|---|---|
| 问句 / 明确诉求（多少钱、能不能、什么时候…） | **2 秒** | 客户在等答案，销售不该干等 |
| 已连发 ≥2 条（非问句） | **3 秒** | 客户在补充说明，比单条陈述更接近说完，但仍留一点合并余地 |
| 单条陈述 | **8 秒** | 宁可多等，也不要抢答 |

- 界面显示的是**服务端算出来的真实秒数**（如"客户这句在等答复 —— 约 2 秒后统一判断"），不是写死的文案
- 客户继续打字会顺延（重新计时），但最长不超过 3 个窗口；兜底扫描按**最长档**判定，绝不会抢在正常窗口前面动手
- 配置：`MESSAGE_BATCH_WINDOW_MS`（陈述档，默认 8000）与 `MESSAGE_BATCH_FAST_WINDOW_MS`（问句档，默认 2000）；
  **把两者设成相同值即可退回旧的固定窗口行为**

**为什么值得这么做（一句话）**：判断慢不等于模型慢。实测「客户最后一条消息 → 销售看到判断」从 **10.2 秒降到 4.6 秒**，
而模型本身只占其中 1–4 秒 —— 剩下的等待量本来就是我们自己加的。

### 3.8 Follow-up 跟进

客户详情页右侧「跟进」区块显示**当前判定结论与理由**，并提供两个按钮：

- **模拟静默 30 分钟**：把该客户的整段对话整体后移，立刻复现"客户静默超时"
- **立即扫描跟进**：满足条件就生成跟进建议（复用同一条 pipeline）

判定规则（9 条短路，前 8 条都是"不跟进"）：终态 / 已转人工 / 已有待办 / 超过次数上限（2 次）/ 冷却期内 / 从未说过话 / 未到静默阈值（2 分钟）/ 销售刚回过话 → 不跟进。

### 3.9 AI 日志与成本（`/ai-logs`）

六个指标卡：调用次数 / token 消耗 / 估算成本 / 降级失败次数 / **AI 建议采纳率** / **人工修改率**；
下方是最近 50 次调用的明细（含原始错误信息、重试次数、规则守护结果）。

**这张表怎么用来排障**：
- 状态列「已降级」→ 那次 AI 调用失败，系统按兜底话术转人工
- 「重试 n」→ 多半是输出被截断后放大了预算重试
- 修改率偏高 → 不是 bug，是产品信号：应该回企业规则页补规则或补示例
- 「耗时」列是**模型真实耗时**（响应体读完才计时）。想知道时间花在哪 —— 窗口、模型生成还是落库
  —— 点每行的 **「查看链路 →」**

### 3.9.1 判断链路详情（`/ai-logs/[id]`）

把"这一次判断到底怎么来的"完整摊开，是**排障**与**设计复盘**都最有用的一个页面：

| 区块 | 内容 | 回答什么问题 |
|---|---|---|
| 结论条 | 总耗时 / 模型耗时（含首字节）/ token / 调用次数 | 这次花了多少 |
| **环节耗时** | 载入上下文 → 组装提示词并调用模型 → 状态机+规则守护+交接 → 写入建议+乐观锁（带条形图） | **时间花在哪** |
| 这一步判了什么 | 六字段结果 + 状态流转 + 系统对 AI 建议的每一处修正（带规则码） | 系统采纳了什么 |
| 护栏做了什么 | 规则守护违规 / 改写次数 / 交接规则触发说明 | 为什么升级人工 |
| 送进模型的上下文 | 历史消息数、本轮消息数、企业规则数、敏感词数、finish_reason、max_tokens | 模型看到了什么 |
| **原文对照** | 模型收到的 system/user prompt ↔ 模型的原始输出 ↔ 最终落库的回复 | 差异就是护栏介入的地方 |

> 真实案例：M9 那次"判断要等很久"，就是靠这个页面的前身（分段耗时日志）发现
> **模型耗时埋点记的是首字节而不是总时长**（220ms vs 真实 2600ms，差 10 倍）。
> 没有分段耗时，排查会一直指向错误的方向。

### 3.9.2 客户列表 = 待办队列（`/customers`）

列表**不是按"最近更新"排的，而是按"我现在该处理谁"排的**：

| 优先级 | 标签 | 判据 |
|---|---|---|
| 最高 | **需要人工** | 已标记需人工介入（投诉 / 高价值 / 规则红线） |
| ↓ | **该跟进** | 客户说过话且静默超过阈值 |
| ↓ | **待回复** | 客户刚说完话，轮到我们了 |
| ↓ | 待判断 | 客户还没说过话 |
| 最低 | 已结束 | 终态（成交/流失），不再打扰 |

顶部三个数字（**需要人工介入 / 该主动跟进 / 待办合计**）让销售一眼知道今天有没有活。
两个刻意的规则：**终态客户如果同时需人工，仍然排最前**（成交后要人工确认也是一件待办）；
排序只影响展示，**不会漏掉任何客户**。

### 3.10 首次判断补跑与加载态

**要解决的问题**：消息不一定都从入口进来 —— 演示种子数据是直接写库的、历史会话可能是导入的、
数据迁移会带过来、进程也可能在聚合窗口期间重启。这些情况下客户**有聊天记录却没有 AI 判断**，
界面就会出现自相矛盾的一幕：AI 卡片说「还没有 AI 判断」，旁边的跟进区块却说
「客户已静默 30 分钟，建议主动跟进」。

**系统怎么处理**（三件事，缺一不可）：

| 环节 | 做法 | 为什么这么做 |
|---|---|---|
| 发现 | 打开详情页时做一次**廉价检查**（`firstJudgmentWait`，不调用 AI）：已有判断 → 不用管；有未归批的客户消息 → 需要补跑；消息已归批但判断还没落库 → 判断正在跑 | 判断"还没开始"和"正在跑"对用户是同一件事：等一会儿就好。只看第一种会让**第二次刷新**退回误导性的"还没有 AI 判断"，而且不再轮询 —— 这就是"要刷新好几次判断才出来"的根因 |
| 执行 | 后台任务 `runInitialJudgment()`：把这些历史消息归到同一批，标记 `trigger=INITIAL_BACKFILL`，走**同一条主干 pipeline** | 不在页面渲染里 `await` 这次 AI 调用，首屏不会白等 1–3 秒；补跑与正常判断共用主干，规则守护、交接策略、留痕一个都不少 |
| 呈现 | 立即渲染「AI 正在补跑首次判断…」+ 转圈 + 已等待秒数；前端每 2 秒轮询，判断落库后**自动刷新**；超过 15 秒追加兜底提示 | 用户看到的是进度，不是"没反应"；全程不需要手动刷新 |

**卡片上的两种说明文案是互斥的**（这一点也被自动化断言守着）：

- 补跑：`这条判断基于该客户此前的 N 条历史消息 —— 系统发现这些消息还没有被判断过，自动补跑了一次`
- 连发：`本轮把客户连续发送的 N 条消息合并为一次判断（否则会连续回复 N 次）`

> 为什么专门强调文案：早期版本对两种来源用了同一句话，于是"逐条聊了半小时"被说成
> "客户连续发了 3 条" —— 功能是对的，但**解释是错的**，一眼就会让人怀疑整个合并逻辑。

### 3.11 重置演示数据为什么不打断你

`POST /api/admin/reset` 可以随时把演示数据恢复干净（演示前、评审前、现场演示翻车后都能用）。
它按**唯一键 upsert**：租户按 `slug`、用户按 `email`、客户按 `(tenantId, handle)` —— **id 全部不变**。

于是：
- 已登录的浏览器**不用重新登录**（会话 Cookie 里的用户/租户 id 仍然有效）；
- 已经打开的 `/customers/<id>`、收藏的链接、浏览器回退**都还能用**（否则会 404）；
- 只重建聊天记录 / AI 建议 / 客户状态 / 跟进任务，非种子客户（例如自动化测试创建的）会被清掉。

## 6. 演示脚本（12 分钟 Demo Show）

### 第 1 幕（1 分钟）· 系统是什么

> "这是 ZigoAI Mini，一个 AI 销售助手。它的定位不是替代销售，而是帮销售判断客户现在处于哪一步、下一步该做什么，并给出一句可以直接发出去的话。"

打开 `/customers`（用乐蒙销售登录）→ 指出列表里的**阶段标签**与**建议人工介入**标记。

### 第 2 幕（3 分钟）· 一条消息进来之后发生了什么

进 **张女士** → 发「你们年卡多少钱？」→ 讲解等待窗口（连续消息合并）→ 卡片出现后逐项讲：
- 客户意图 / 阶段 / 下一步动作
- **引用企业规则 R1/R2**（悬停看原文）："规则不是写在文档里的摆设，它逐条编号进了提示词，而且模型必须回报引用了哪几条"
- 判断依据 + 建议回复

> **这一句值得单独讲**（它是这一轮优化里最有说服力的一段）：
> "客户问了价格，界面告诉销售的是『约 2 秒后统一判断』—— 如果客户只是在陈述（'我考虑一下'），窗口会放宽到 8 秒。
> 窗口长度按**客户说完了没有**自适应，因为**判断慢不等于模型慢**：
> 实测从『客户最后一条消息』到『销售看到判断』从 10.2 秒降到 4.6 秒，而模型本身只占 1–4 秒。
> 我们连自己的耗时埋点都查过 —— 它原来记的是首字节时间（220ms），真实值是 2.6 秒，差了 10 倍。"

### 第 3 幕（2 分钟）· 系统不完全信任模型

进 **黄总**（已成交）→ 发「算了，我再考虑考虑，先不报了。」
→ AI 依然会建议把阶段降下来，但**卡片上出现「系统对 AI 建议的修正：AI 建议『已流失』→ 采纳『已成交』」**

> "模型输出的是**建议**，数据库里的状态是**事实**。中间隔着确定性状态机：终态保护、阶段不回退、需人工只升不降。这一块就是我说的'不完全信任模型'。"

### 第 4 幕（2 分钟）· 销售的真实工作流

回到张女士 → 改一下建议回复 → 点发送 → 指出「销售实际发送」留痕

> "发出去的是人确认过的文本。而且留痕之后，我可以算出 AI 建议的采纳率和修改率 —— 这是'AI 到底有没有用'的量化答案。"

### 第 5 幕（2 分钟）· 不同企业的规则真的不一样

换 `sales@jixie.demo` → 进 **王老板** → 发「保费大概 1500 元够吗？」
→ 「达到企业阈值 1000 元，按交接规则转人工」

> "乐蒙同样的金额不会转人工。转人工标准取决于客单价和风险：乐蒙一节课几百元可以自动跟，机械之家一单保费上千、还涉及承保责任，就必须人工核保。"

再用主管账号打开 `/tenant/config` → 演示**规则试跑对比**：把阈值改成 100 → 同一句话立刻变成转人工，且**不落库**。

### 第 6 幕（1 分钟）· 客户不回复怎么办

进任意客户 → 点「模拟静默 30 分钟」→ 判定理由变化 → 点「立即扫描跟进」→ 生成跟进建议

> "判定有 9 条规则：终态不管、已转人工不管、超过次数上限不管、刚回过话不管……这些都写成纯函数，能单测也能逐条解释。"

## 7. 常见问题与排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 点登录没反应 / 又回到登录页 | 会话 Cookie 的 `Secure` 标记与 HTTP 不匹配（历史问题） | 已在 1.2 修复；确认部署的是 1.2+ |
| 点「模拟客户发来」没反应，控制台报 `crypto.randomUUID is not a function` | 非安全上下文不支持该 API（历史问题） | 已在 1.2 修复 |
| 发消息后输入框一直"发送中…" | 聚合窗口等待被错误地同步阻塞（历史问题） | 已在 1.4 修复 |
| 服务打不开、`curl` 无输出 | 容器退出（最常见：`.env` 值带了引号导致连接串非法） | `docker ps -a` 看状态 → `docker logs` 看报错 → `.env` 写成 `KEY=值` **不带引号** |
| `/api/health` 显示 `database.ok=false` | 数据库容器没起来 / 网络不通 | `docker exec zigoai-db pg_isready -U zigoai`；确认两容器都在 `zigoai-net` |
| `/api/health?deepseek=1` 报 `ByteString` 错误 | API Key 里含非 ASCII 字符（通常是粘贴了中文占位符） | 换成真实 Key |
| AI 卡片显示「已降级为人工」 | AI 调用失败（超时/网络/额度） | 看 `/ai-logs` 的 errorMessage 与 errorKind |
| 想恢复干净演示数据 | —— | `curl -s -X POST -H "x-seed-token: <口令>" http://127.0.0.1:8080/api/admin/reset` |
| 想看数据库 | —— | `docker exec -it zigoai-db psql -U zigoai -d zigoai` |

## 8. 已知限制（主动交代）

1. **不接真实微信**：发送是模拟的，但数据流与真实场景完全一致（入库并参与下一轮判断）
2. **判断是同步的**：客户消息进来后由后台在窗口关闭时判断，不是"消息入库立即返回 + 任务队列 + 前端推送"
3. **定时器是进程内的**：多实例部署时应换成 Redis 延迟队列（当前靠 batchId 幂等，不会重复调用 AI）
4. **规则改动没有版本与回滚**：改了即生效，没有变更历史表
5. **没有做知识库 / RAG**：AI 对该企业的了解只来自"规则配置 + 当前对话历史"，题目也不建议在此花时间
6. **`Follow-up` 没有接真正的调度器**，靠 `pnpm agent:scan` 或外部 cron
7. **时间旅行是演示工具**，会真的修改消息时间戳，生产不应暴露
8. **窗口的自适应判据是启发式的**：靠问句标点、疑问助词与诉求词表估计"客户说完了没有"，
   拿不到微信的"正在输入"状态。判错代价很小（下一条消息会重置窗口），但不如真实输入状态可靠
9. **连发中间停顿超过窗口会拆成两次判断**：窗口被压短之后，"响应快"与"合并全"的边界更靠前了
   （陈述档 8 秒内仍会合并，连发档只有 3 秒）。这是刻意取舍，也说明"追认"机制值得做
10. **延迟的大头仍在模型侧**：窗口已压到 2–3 秒，模型要 1–4 秒（会先生成推理 token）。
    再快就得动模型侧：流式输出、更快的非推理模型，或"先秒回一句再补完整判断"
